#### Принятое архитектурное решение
Для MVP предлагается выделить вокруг текущего интернет-банка и АБС отдельный контур цифрового депозитного процесса, не реализовывать новую функциональность напрямую в ядре интернет-банка и не усиливать прямую нагрузку на АБС.

В центре решения вводятся новые компоненты:

1. **Deposit Application Service**  
   Сервис приёма и маршрутизации заявок на депозит из сайта и интернет-банка. Отвечает за:
    - создание заявки
    - хранение статуса заявки
    - передачу заявки в кол-центр или в бэк-офисный контур
    - публикацию событий о смене статуса

2. **Rate Management Service**  
   Отдельный сервис или модуль управления ставками. Отвечает за:
    - хранение актуальных ставок
    - публикацию ставок в сайт и интернет-банк
    - поддержку персонализированных/специальных ставок
    - разграничение доступа для депозитного и кредитного бэк-офиса
    - отказ от XLS как от основного операционного инструмента

3. **Notification Service**  
   Внешний по отношению к ядру интернет-банка сервис, реализующий:
    - отправку одноразовых СМС-кодов
    - отправку СМС-уведомлений о подтверждении ставки
    - отправку СМС об открытии депозита

   Такой вариант выбран, чтобы не дорабатывать vendor-ядро интернет-банка, хотя внутри банка уже есть функциональность, связанная с СМС.

4. **ABS Adapter / Anti-Corruption Layer для АБС**  
   Прослойка интеграции между новыми сервисами и АБС. Отвечает за:
    - изоляцию клиентских каналов от legacy-модели АБС
    - преобразование запросов и статусов
    - буферизацию интеграционных вызовов
    - снижение риска прямой перегрузки АБС

5. **Deposit Api**  
   Для отображения депозитных продуктов и ставок сайт и интернет-банк должны получать данные не из АБС напрямую, а из специализированного API с поддержкой кэша. Это позволит улучшить latency и не повторять текущую проблему медленной загрузки.


#### Логика выбора технологий
При выборе подхода использовались следующие принципы:

1. **Минимум изменений в legacy-core**
   Интернет-банк является монолитом на vendor-платформе, обновление ядра зависит от подрядчика. Поэтому новая логика должна выноситься в отдельные сервисы, интегрируемые с текущим интернет-банком.

2. **Минимизация нагрузки на АБС**
   БД АБС уже перегружена, а сама АБС может масштабироваться только вертикально. По этой причине клиентские каналы не должны напрямую читать и особенно массово писать в core-систему.

3. **Совместимость со стеком банка**
   Новые компоненты допустимо реализовать на .NET или Java с использованием MS SQL/Oracle, так как в банке уже есть компетенции по этим технологиям.

4. **Подготовка к дальнейшей декомпозиции**
   MVP должен стать первым шагом в сторону выделения депозитного домена. Поэтому целесообразно сразу выделять отдельные контексты:
    - управление ставками
    - управление заявками
    - уведомления и OTP
    - интеграция с АБС

5. **Асинхронность там, где это снижает риски**
   Где возможно, взаимодействие с АБС и уведомлениями лучше строить событийно или через очередь. Kafka может быть целевой технологией на будущее, но с учётом несовместимости текущего ядра интернет-банка на этапе MVP допустима промежуточная интеграционная реализация без прямого внедрения Kafka в интернет-банк.

6. **Разделение online UX и back-office обработки**
   Пользователь должен мгновенно получать подтверждение приёма заявки, даже если окончательная обработка выполняется вручную позже менеджером бэк-офиса.

### <a name="_bjrr7veeh80c"></a>**Альтернативы**

#### Альтернатива 1. Реализовать весь новый процесс внутри АБС
Суть:
- формы и логика заявок реализуются в АБС
- интернет-банк и сайт напрямую вызывают АБС

Плюсы:
- меньше новых систем
- проще сохранить текущую бизнес-логику
- АБС остаётся единой точкой правды и исполнения

Минусы:
- усиливается нагрузка на уже перегруженную АБС
- ухудшается масштабируемость
- online UX начинает зависеть от latency АБС
- растёт связность с legacy
- сложнее развивать сайт и интернет-банк независимо

#### Альтернатива 2. Дорабатывать vendor-ядро интернет-банка
Суть:
- логика депозитов и OTP реализуется прямо в монолите интернет-банка.

Плюсы:
- единый клиентский контур
- меньше внешних вызовов со стороны интернет-банка

Минусы:
- высокая зависимость от подрядчика
- рост стоимости изменений
- низкая скорость развития
- сложнее переиспользовать решение для сайта

#### Альтернатива 3. Оставить XLS и email как есть, цифровизовать только фронт часть
Суть:
- сайт и интернет-банк только создают заявки
- ставки и вся логика остаются на ручном процессе

Плюсы:
- минимальная стоимость MVP
- быстрый старт

Минусы:
- сохраняется ключевой операционный bottleneck
- невозможно обеспечить качественный UX
- сложно масштабировать объём заявок
- не создаётся фундамент для финального состояния через год
