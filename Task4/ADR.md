### <a name="_qmphm5d6rvi3"></a>**Решение**

- [Диаграмма контекста](./Context.puml)
- [Диаграмма компонентов](./Component.puml)

#### Принятое архитектурное решение

В качестве единого источника опубликованных ставок используется Deposit Rate Distribution Service. Вокруг него добавляются два канала распространения:

1. Внутренний контур (online):
   - публикуется `Rate API` для чтения опубликованных ставок
   - система кол-центра банка получает ставки по API и показывает их операторам
   - тем же API пользуются сайт и интернет-банк, чтобы все каналы видели одинаковый набор условий

2. Внешний контур партнёра (file-based):
   - после публикации ставок `Partner Export Processor` формирует внешний файл обмена
   - файл содержит только опубликованные ставки и служебную метаинформацию версии
   - файл передаётся партнёру по согласованному файловому процессу
   - партнёрский кол-центр использует последнюю полученную выгрузку

#### Недостатки выбранного решения

1. Партнер может получать неактуальные данные. Оператор партнёра видит не online-данные, а последнюю успешно полученную выгрузку.
2. Появляется ещё один интеграционный поток. Нужно сопровождать формат файла, расписание выгрузки и регламент обмена.
3. Потребуется доработка системы кол-центра банка. Нужен новый экран или виджет ставок и интеграция с внутренним API.
4. Нужен контроль канала обменна файлами.


### <a name="_bjrr7veeh80c"></a>**Альтернативы**

#### Альтернатива 1. Давать внутреннему и партнёрскому кол-центру доступ к XLS напрямую

**Суть:** продолжить текущий процесс и распространять XLS-файлы как есть.

**Плюсы:**
- минимальное количество изменений
- привычный для бек-офиса процесс

**Минусы:**
- XLS остаётся источником правды
- высокая вероятность рассинхронизации между каналами
- нет контролируемой публикации и версии

#### Альтернатива 2. Интегрировать оба кол-центра по API

**Суть:** и внутренний, и партнёрский кол-центр получают ставки по API.

**Плюсы:**
- единый технический паттерн
- высокая степень актуальности данных

**Минусы:**
- не соответствует ограничению партнёра
- повышает стоимость и срок MVP
- требует внешней интеграции

#### Альтернатива 3. Реализовать распространение ставок через АБС

**Суть:** АБС становится центральной точкой выдачи ставок для call-центров и партнёра.

**Плюсы:**
- меньше новых доменных компонентов;
- логика ближе к текущему процессу.

**Минусы:**
- усиливает зависимость от АБС;
- создаёт дополнительную нагрузку на АБС;
- затрудняет развитие цифровых каналов отдельно
